# NYC Cleaning Comprehensive SEO Audit

**Audit date:** July 17, 2026  
**Application audited:** NYC Cleaning managed full-stack website  
**Canonical origin:** `https://www.nyccleaning.co`  
**Method:** Source review, server-rendered HTML crawl, HTTP control checks, structured-data inspection, media and internal-link validation, Vitest, TypeScript, production builds, Lighthouse, and responsive visual review.

## Executive summary

The audit covered every canonical URL exposed by the site’s sitemap, all crawl-control endpoints, representative aliases and error states, every discovered image and social-preview resource, and every canonical internal destination. The initial application crawl found **45 titles over 60 characters**, several groups of duplicate titles and descriptions, duplicate archive URLs, missing permanent redirects, incomplete article schema, inaccurate sitemap modification dates, CMS Insights absent from sitemap generation, legal pages included despite being utility content, and hydration or first-paint inconsistencies affecting dynamic articles and development SSR.

All justified application-side issues were corrected. The final dynamic sitemap contains **146 canonical indexable URLs**. The definitive crawl found **zero route-level SEO defects**, **zero duplicate titles or descriptions**, **zero missing schema, canonical, title, description, H1, or image-description issues**, and **zero failed or redirecting canonical internal destinations**. The media audit verified **239 unique assets** without failures. The completed application has **189 passing automated tests**, a clean TypeScript check, and a successful production build.

One material external action remains: `www.nyccleaning.co` still serves the prior host rather than this managed project. The application is ready, but its improvements cannot replace the legacy public site until the custom domain is connected to the current project.

The implementation follows Google’s guidance that pages must be publicly accessible, return successful HTTP responses, contain indexable content, and not block Googlebot; Google also recommends descriptive titles and headings, crawlable links, useful image alt text, consistent canonical signals, accurate sitemaps, and valid structured data.[1][2][3][4]

## Findings and implemented corrections

| Finding | Risk | Correction completed |
|---|---|---|
| Long and duplicate search titles | Search engines could rewrite titles or show indistinct results | Added a centralized metadata resolver with concise, route-specific page and Insight titles, including intentional differentiation for legacy duplicate articles |
| Duplicate archive metadata | Monthly archives and alternate archives competed with the main archive | Added month-specific archive titles, descriptions, headings, and canonicals; removed the duplicate `/blog/` archive from the canonical inventory |
| Alias URLs rendered as 200 pages | Duplicate URLs could be crawled despite canonical tags | Added permanent redirects for public aliases and retained canonical internal links so visitors and crawlers avoid redirect hops |
| Unknown routes inherited homepage-like client behavior | Error URLs could briefly expose loading or mismatched content | Added true server 404 responses, `noindex`, dedicated 404 metadata, and serialized missing-route hydration parity |
| `/admin` could inherit a server 404 | Authenticated CMS entry could receive an incorrect status | Added explicit admin SSR handling with successful status and `noindex, nofollow` |
| Privacy and terms utility pages were indexable | Low-value utility URLs consumed sitemap coverage | Added `noindex, follow` and removed them from the canonical sitemap while retaining public access and footer links |
| Article structured data lacked complete author/publisher/image/date details | Rich-result eligibility and entity clarity were weaker | Added complete BlogPosting fields using only stored or verified facts, including dateModified where available |
| Sitemap modification dates were generated at build time | Search engines received inaccurate freshness signals | Switched static routes to source dates and dynamic CMS Insights to stored publication/update timestamps |
| Published CMS Insights were absent from static sitemap output | New articles could depend only on internal discovery | Added a server-generated CMS-aware sitemap containing published articles only, with deterministic static fallbacks |
| Robots and sitemap behavior could drift | Dynamic and generated crawl controls could disagree | Centralized builders, aligned dynamic/static output, and added explicit admin/API disallow rules plus one canonical sitemap declaration |
| CMS Insight SSR and hydration could diverge | Users could see a loading flash and hydration mismatch despite crawler-visible HTML | Serialized the server-prefetched published article into the client’s first render and added safe escaping |
| Development SSR configuration could lose the configured client root | Managed preview routes returned transient 500s after a restart | Resolved the Vite configuration before programmatic server creation and added a regression guard |
| Global CSS was not guaranteed on the first development SSR paint | Full-page screenshots exposed an unstyled first paint before hydration | Made the stylesheet a document-level Vite dependency for both development and production |
| Homepage media and public bundle were heavier than necessary | Synthetic performance and image delivery were weaker | Added responsive hero variants and preload hints, compressed six service-card assets, lazy-loaded below-fold media, set decoding/intrinsic dimensions, removed production source-location attributes, and code-split authenticated CMS routes |
| Footer eyebrow contrast failed one Lighthouse check | The call-to-action label did not meet contrast expectations | Increased the footer eyebrow contrast and locked the value with a regression |
| Viewport and favicon markup were incomplete | Accessibility and search-result brand presentation were weaker | Removed restrictive maximum-scale behavior and added the deployment-safe favicon |

## Final validation

The final crawler used the application’s dynamic sitemap as its source of truth and fetched all **146 canonical routes** while expecting production-domain canonicals. All returned 200, all exposed one H1, every title and description was present and unique, every title was at most 60 characters, every description was at most 160 characters, every page contained structured data, and no canonical or robots mismatch remained.

The media and link validator inspected **239 unique assets** and **146 unique canonical internal destinations**. It found no failed assets, no failed internal destinations, and no redirecting internal destinations. Representative permanent aliases returned 301, legal pages returned 200 with `noindex, follow`, `/admin` returned 200 with `noindex, nofollow`, and unknown routes returned a true 404 with no loading-shell hydration mismatch.

The final quality gate completed **34 passing test files and 189 passing tests**, followed by a clean TypeScript check and successful client/server production build. Current server, browser-console, and network logs contained no post-validation application errors. Desktop and mobile captures verified the homepage, service detail, Insights archive, preserved article, and true 404 templates after the first-paint stylesheet correction.

### Lighthouse context

The definitive isolated production-bundle run scored **100 SEO** and **100 accessibility**, with **0.023 cumulative layout shift** and **30 ms total blocking time**. Its synthetic performance score was **55**, with a 14.4-second LCP under the local throttled environment. The report also recorded 3.09 MB transferred, including signed remote storage assets and audit-runtime instrumentation. All measured application-controlled defects were addressed: hero discovery, image payloads, below-fold loading, public-bundle composition, contrast, hydration mismatch, and source-location markup. The remaining local best-practice deductions were generated by the Manus debug collector’s missing development logging endpoint and its deprecated unload listener, neither of which is part of the production application source.

Lighthouse is a lab diagnostic rather than a field ranking guarantee. After domain migration, real-user Core Web Vitals should be monitored in Search Console and PageSpeed Insights before making further performance tradeoffs.[5]

## Required external launch action

The canonical origin `https://www.nyccleaning.co` still resolves to the prior hosting environment. During the initial comparison, that host returned three 404s for URLs already present and valid in the managed application. Application code cannot change DNS or domain assignment.

Connect the existing custom domain in the project’s **Settings → Domains** panel, update the registrar records exactly as shown there, confirm both apex and `www` resolve to the managed deployment, and preserve the application’s canonical `www` origin. After DNS propagation, submit `https://www.nyccleaning.co/sitemap.xml` in Google Search Console and request validation for representative homepage, service, archive, and Insight URLs. This is a migration action, not a code defect; the managed application is already configured to serve the required canonicals, redirects, robots directives, sitemap, and SSR content once the domain points to it.

## Post-launch monitoring

For the first four weeks after domain migration, review Search Console indexing, sitemap processing, Page Indexing exclusions, Core Web Vitals, HTTPS status, and enhancements weekly. Compare indexed URLs against the 146-route canonical inventory, investigate unexpected “Duplicate without user-selected canonical” or “Crawled—currently not indexed” clusters, and monitor server logs for crawler-visible 5xx responses. Avoid changing established canonical paths unless a documented permanent redirect is added at the same time.
